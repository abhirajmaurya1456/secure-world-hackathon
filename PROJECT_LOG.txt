============================================================
2. INITIAL PROJECT DEFINITION
============================================================

Problem:
Phishing and malicious URLs can trick users into visiting fraudulent pages
or revealing sensitive information.

Initial target:
A system that analyzes a URL/message, identifies phishing risk, and explains
the evidence behind its decision.

Core principle:
Do NOT build only:
    input -> third-party AI API -> phishing/not phishing

Instead, build our own meaningful security pipeline involving feature
extraction, security rules and/or an ML model, testing, metrics, and an
explanation layer.

Initial intended output:
- risk score
- verdict
- reasons/evidence
- detailed analysis
- testing metrics

3. THREAT MODEL — VERSION 0.1
============================================================

Asset:
- user credentials
- sensitive/personal information
- account access
- potentially financial information

Attacker:
- malicious actor/phisher attempting to deceive a user

Target/Victim:
- person receiving a malicious URL/message

Attack Surface:
- URLs
- email messages
- SMS/messages
- links leading to fraudulent pages

Possible Attack Vector:
Attacker sends a deceptive link/message -> user clicks the link ->
user reaches a malicious/fraudulent destination -> sensitive information
may be exposed.

Potential Impact:
- credential theft
- account compromise
- data exposure
- financial/social-engineering consequences

Defensive Goal:
Detect suspicious/phishing URLs before the user trusts or visits them,
and provide understandable evidence for the decision.

NOTE:

techniques and deciding the exact system scope.

========== FEATURE ANALYSIS — INITIAL BASELINE ==========

Dataset:
154,642 URLs

Features:
16 URL-based security features + label

Missing values:
0

Class balance:
Benign = 77,321
Phishing = 77,321

Initial observations:
Phishing URLs in this dataset have higher average values for
URL length, hostname length, path length, query length, dot count,
hyphen count, digit count, special character count, subdomain count,
and suspicious keyword count.

Important dataset-design observations:

1. All generated benign URLs currently use HTTPS.
   Therefore has_https is strongly correlated with the benign class.
   This may introduce dataset-specific bias.

2. Generated benign URLs generally contain only the domain and "/",
   producing path_length ≈ 1 and query_length = 0.
   Natural phishing URLs contain substantially more varied paths
   and queries.

3. Phishing data contains 77,321 URLs from 41,891 unique domains.
   A random URL-level train/test split could therefore cause domain
   leakage.

Decision:
Do not interpret future high model accuracy as sufficient evidence
of real-world performance. Establish a baseline first and use
domain-aware evaluation and robustness testing.

ROBUSTNESS TEST — HTTPS ABLATION
============================================================

Experiment:
The baseline Random Forest used 19 URL-based features,
including has_https.

Because HTTPS was strongly correlated with the benign class
in the dataset, a controlled ablation experiment was performed
by removing has_https completely.

All other conditions were kept the same:
- Same dataset
- Same hostname-aware train/test split
- Same random_state = 42
- Same 300-tree Random Forest
- Same evaluation set

Baseline — 19 features:
- Accuracy: 98.89%
- Precision: 98.95%
- Recall: 98.33%
- F1: 98.64%

Without has_https — 18 features:
- Accuracy: 98.56%
- Precision: 98.75%
- Recall: 97.71%
- F1: 98.23%

Performance change:
- Accuracy: -0.33 percentage points
- Precision: -0.20 percentage points
- Recall: -0.62 percentage points
- F1: -0.41 percentage points

Confusion matrix without has_https:
[[7390, 64],
 [118, 5045]]

Feature importance without has_https:
1. path_length: 30.60%
2. slash_count: 28.56%
3. digit_count: 10.14%
4. special_char_count: 5.75%
5. url_length: 4.97%
6. url_entropy: 4.91%
7. subdomain_count: 4.51%
8. dot_count: 3.58%

Interpretation:
Removing has_https caused only a modest performance decrease.
This suggests that the model's performance is not primarily
dependent on the HTTPS feature alone.

However, path_length and slash_count remain dominant features.
Further robustness testing is therefore required to determine
whether the model is learning generalizable phishing URL
characteristics or dataset-specific URL structure patterns.

Model saved to:
data/model/phishing_model_no_https.pkl

Important observation:

Interpretation:
This indicates a significant generalization/distribution-shift
problem. The model appears to have learned URL-structure
patterns present in the source datasets that do not necessarily
generalize to arbitrary legitimate URLs.

The manual test therefore demonstrates that held-out dataset
metrics alone are insufficient evidence of real-world
generalization.

Next investigation:
Compare feature distributions of legitimate training URLs
against manually constructed legitimate URLs and identify
features responsible for false-positive predictions.

Note:
The manual test was intentionally kept separate from training
and was not used to tune the model before this evaluation.

============================================================
SECURITY ENGINE — CONTEXT LAYER
============================================================

Problem discovered during manual testing:
The ML model produced very high phishing probabilities for some
legitimate well-known URLs such as:

- https://www.google.com/
- https://github.com/login

This occurred because the current ML feature set is heavily based
on URL structural characteristics such as path length and slash count.
The model does not inherently know that a well-known domain such as
github.com is legitimate.

Decision:
Add a small prototype trusted-domain context layer instead of
manually adding large numbers of URLs to the ML training dataset.

Current prototype trusted domains:

- google.com
- stackoverflow.com
- github.com
- wikipedia.org
- microsoft.com

Implementation:
The hostname is extracted from the URL and compared against the
prototype trusted-domain list, including matching subdomains.

Important limitation:
This is NOT a comprehensive safe-URL database and does NOT mean that
every URL hosted on a trusted domain is guaranteed safe.

The trusted-domain list is currently used only as a prototype
context signal to reduce false positives for known domains.

Decision:
Do not manually build a huge allowlist. A future production version
could use maintained reputation/threat-intelligence sources as an
additional signal.

ML GENERALIZATION — IMPORTANT LIMITATION
============================================================

The model showed strong performance on the hostname-aware held-out
dataset but significantly weaker performance on manually constructed
unseen URLs.

Hostname-aware held-out evaluation:

Accuracy: 98.56%
Precision: 98.75%
Recall: 97.71%
F1: 98.23%

Manual unseen URL test:

Total URLs: 12
Correct: 5
Accuracy: 41.67%

Benign URLs:
7 tested
0 correctly classified
7 false positives

Phishing-like URLs:
5 tested
5 correctly classified

Interpretation:
The model performs strongly on the distribution represented by the
training/evaluation dataset but does not generalize reliably to all
arbitrary real-world URLs.

The feature analysis showed that the model relies heavily on URL
structural characteristics, particularly:

- path_length
- slash_count
- digit_count
- special_char_count
- URL length
- URL entropy

This indicates distribution shift and possible dataset-specific
learning.

Important decision:
Do NOT claim that the model's 98.23% F1 means 98.23% real-world
phishing detection accuracy.

The manual test was kept separate from training and was not used for
model tuning before evaluation.

Security-engineering response:
Use the ML model as one signal in a layered detection engine rather
than treating its probability as absolute truth.

Current layered approach:
ML structural analysis
+
deterministic security rules
+
prototype trusted-domain context
=
final risk assessment

Future improvement:
Add stronger domain/reputation/threat-intelligence signals and
evaluate against larger, independently sourced unseen URL datasets.

MODEL 3 — RAW URL CHARACTER MODEL
============================================================

Purpose:
The first two models use handcrafted URL features. Manual testing
showed strong held-out performance but poor generalization to some
legitimate URLs.

A third model was therefore developed using the raw URL string itself.

Pipeline:
Raw URL
→ character-level TF-IDF
→ Logistic Regression
→ benign/phishing classification

Training dataset:
data/processed/real_url_dataset.csv

Feature representation:
- Character-level TF-IDF
- ngram_range = (3, 5)
- min_df = 2
- max_features = 200,000
- sublinear_tf = True

Classifier:
LogisticRegression(
    max_iter=1000,
    class_weight="balanced",
    random_state=42
)

Evaluation:
Hostname-aware train/test split using random_state=42.

Held-out results:
Accuracy  = 99.01%

31. FINAL SECURITY ENGINE V2 — REGION-AWARE DECISION LAYER
============================================================

Production engine:
Security Engine V2 remains the production decision engine.

Architecture:
URL
→ feature extraction
→ Random Forest model
→ raw URL character model
→ security indicators
→ hostname/path/query region analysis
→ known-domain contextual evidence
→ final risk score
→ SAFE / SUSPICIOUS / PHISHING
→ human-readable explanation

Region-aware logic:
- Query-string complexity is treated as weak evidence because
  legitimate applications commonly use IDs, UUIDs, tracking parameters,
  session values and other query parameters.
- Deep/numeric path structures receive stronger attention.
- Security-sensitive path and query semantics are considered as
  contextual evidence rather than automatic proof of phishing.
- Strong structural indicators such as IP addresses, @ symbols,
  punycode, non-standard ports and multiple suspicious keywords
  retain strong influence.
- Known-domain information is treated as contextual evidence rather
  than an automatic safe-list.
- Known domains without strong phishing indicators receive a
  contextual reduction in model risk.
- Strong phishing indicators are not suppressed merely because a
  domain is known.

Final contextual adjustment:
For a known domain with no strong indicators and high model risk,
ensemble probability is multiplied by 0.35.

This adjustment reduced false alarms on legitimate known-domain URLs
without introducing phishing false positives in the current evaluation.
